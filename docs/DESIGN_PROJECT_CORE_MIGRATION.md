# Remaining project core migration

Status: project-core ownership contract and migration exit checklist, following
the delivered semantic/desktop/panel batch on main597fee38. Release acceptance
requires the exact-candidate records and CI; this document does not certify a run
or claim that all twelve original architecture findings are closed.

## Facts and owners

Original source bytes, row domains, units and scientific provenance remain truth.
Scientific logical IDs and original locator strings are independent of the local
filesystem location. Managed documents own represented science/presentation;
Legacy/NativeSuite saved native bytes own their complete visual state. A native
cache, GUI draft, transport key or generation number cannot substitute for those
facts. Veusz remains the native renderer/editor adapter.

Retained operator versions own calculation and parameter admission, including
their actual immutable implementation closure. New versions are additive. A
legacy descriptor has an explicit retained implementation mapping; unknown or
missing versions refuse execution and cannot silently refresh the science.
Host grants separately admit external executor identity/action/source scope.
Model labels, hashes and project files do not create execution permission.

ProjectCommands owns normalized command admission, exact preview decisions,
effect preparation after admission and storage-only continuation. Discardable
private render/export/QA computation may precede that admission under the bounded
rule below; it has no durable exactly-once computation promise. FileProjectStore owns the
only durable command records, complete generations and authoritative project
head. Existing native/spec/manifest/delivery paths are verified materializations.
Semantic FileProjectRepository retains its validation and logical revision model;
when attached to a project its physical head/journal/CAS writes use the same
generation owner. A namespace backup is read-only evidence, never another head.

The source location port is explicit per request and resets on every exit.
Cold and pooled native requests bind the trusted selected project/generation and
finite resource roots. Stored specs, scientific source IDs and historical hashes
are not rewritten to make relocation work. Same-name files do not reconnect.

A known content-byte version travels through capture, table/text/sheet IO,
scientific audit, candidate preparation and publication archival. A directory or
semantic composite hash cannot stand in for one file's byte version. Recapture
checks the captured version and identity again; generic initial discovery does
not invent an expected hash. Physical delivery existence uses its selected host
resource capability, not an immutable scientific directory cache.

## Command and failure rules

Native mutation preparation follows reserve, admitted applying, immutable candidate
seal, decision, complete generation, atomic head and verified materialization.
An unsealed uncertain execution never runs again automatically. A complete sealed
candidate has a durable accepted state before head publication and can finish
without executing the native edit again. Export-only continuation is separate
from applying the committed native/scientific effect.

An existing saved-project export enters that publication owner directly. It
audits and, when valid, explicitly adopts the exact current native bytes; it
cannot prepare a replacement from an older generation. Compact figure receipts
come from that committed publication's read/CAS snapshot, not an independently
read earlier registry. Selected suite export receipts overlay the immutable
creation baseline, preserving unselected figures and explicit empty exports.

Legacy native operations are read-only migration inputs. Import requires the
complete finite candidate/decision evidence and a new exact-current scientific
audit; mutable legacy files alone cannot authenticate historical execution or
authorize another native edit. Import a legacy pending operation at its original
verified locations before creating the official whole-project bundle. The new
typed outcome and its frozen evidence can then travel through normal bundle
continuation. Direct relocation of an unimported absolute-path legacy journal
is not claimed; ambiguous or incomplete evidence remains an explicit refusal.

Already captured semantic bytes use publish_prepared with a digest of the exact
writes, artifacts, result and prepared source versions. It has no native callback.
An interrupted prepared-storage seal may finish its original bytes; an interactive
preview cannot be accepted by that path.

Read-only queries do not repair or replace active native files. Resume validates
the original key, project and command binding before recovery. Invalid target
membership must fail before import, recovery or any other write.

The committed outcome also owns its materialization plan: installation generation,
parent and complete member set are derived from immutable reachable history.
Mutable receipt hints must match, and a later resource writer removes an older
receipt's right to reinstall its old preimage. Command filenames, keys and the
committed receipt census must agree before repair or new admission. A missing
committed receipt is an explicit recovery conflict, never a new command or an
instruction to recreate its effect.

A checked history is a derived validation result for one locked Store IO epoch,
not another state owner or a reusable pass. The complete immutable parent chain
is validated once within that batch; mutable receipt identity and membership,
sealed candidates, CAS and physical resource checks remain required. Metadata
writes and the end of the outer physical lease invalidate that result, including
descriptor reuse and nested operations. Installation separately obtains a fresh
last-writer decision; a read-only completed outcome cannot authorize old-byte
installation. No validation result survives into a later operation.

Executable deliveries are inspected through the selected materialized host
resource capability. A read-only scientific directory view cannot prove that a
user launcher is executable or that its delivery root owns this project. Logical
root/request/source identities remain distinct from their host IO locations;
content, executable mode, binding and exact package membership must still agree.
A finite file capability for a ZIP or source parent never grants whole-directory
enumeration. Cold continuation requires explicitly registered host locations,
not an old absolute path or a same-named foreign package.

Literal common/style edit checkpoints are intent resources, not execution
journals. Default entries inside an attached or recognized project use that same
Store; explicit external entries retain their independent request-file owner.
One entry lease keeps the selected project runtime through bound replay and owner
cleanup, including when the original project is offline. Rebinding physical host
locations does not rewrite the frozen intent or bypass namespace/source/output/
revision protections.

Private render/export/QA preparation may discover its output membership before
publication only when it changes no active/source/delivery files. This exception
does not admit external executor effects or GUI mutations. Existing records are
checked first; child shutdown and original wait precede any safe preparation retry.

Selected operations bind exact bytes plus fixed domain projections. Their typed
projected writes merge only the selected fields under the writer lease, retaining
unrelated current entries. Full resource writes retain exact CAS. Whole-set
operations also bind member names; additions cannot evade a read set containing
only previously existing files. There is no generic force flag or JSON patch.

One head switch cannot atomically replace files across separate roots. The durable
installation intent instead yields complete old state, complete new state, or
explicit recovery. Foreign bytes are preserved and block recovery. All trusted
roots share deterministic kernel lease ordering; finite ZIP capability never
scans an entire source/project parent. No power-loss or distributed-lock claim.
